## Integration order

1. Review isolated commits for security/behavior and reject unsafe candidates rather than hiding their gaps. Keep one writer per overlapping file; import via local fetch and deliberate merge or cherry-pick, resolving conflicts without discarding newer evidence.
2. Complete missing provider/deployment inputs and the release closure; set exact tenant/brand/KMS/domain values only from verified owner state. Never open mailbox/login or recording gates from a placeholder probe.
3. Run typecheck, focused behavioral tests and the full changed CLI/API paths once the integrated source is stable. Run the actual browser/mobile and multi-actor flows against the deployed revision; capture expected and observed values and negative controls.
4. Exercise backup/restore before migration and measure egress/load/recovery on the same deployment. Only then reconcile Fusion's failed run and perform the backup/CAS protected root merge without overwriting unrelated edits; verify the merged local and private remote revision independently.

## Material choices and current rationale

- Self-host traffic uses an explicit production `same-origin`/`ALL` build and fails closed on partial flags rather than quietly routing to hosted Macro. This is not an egress firewall; actual flows must still be measured.
- Corporate mail remains provider-backed, not a Mailpit/fixture substitution. Missing Enterprise administration, KMS and public mail routing are real prerequisites, not reasons to mark the gate passed.
- Brand writes require a trusted installation-owner organization ID; choosing an arbitrary existing org would silently grant the wrong IT admins authority.
- The backup/CAS integration route preserves the owner's main tree. A failed late Fusion run and provider-blocked acceptance justify withholding the root merge, while independently accepted source changes can still be committed privately.
