# Диагностика 32 карточек in-review/failed

Срез для этой матрицы: `docs/specifications/failed-evidence.json` от 2026-09-29, сопоставленный со снимком `docs/rus-ctn-inventory.json` от 2026-09-25. Матрица включает ровно 32 уникальных ID, у которых в inventory одновременно `column=in-review` и `status=failed`; `failed` здесь — состояние Fusion, не синоним упавшего CI. Источники парных исследований — 16 записей `failedPairs` в evidence (карточки, их `task.json`, `PROMPT.md`, отчёты/review workflow и журналы); далее отдельно указаны их пределы. Ссылки на спецификации по карточкам зарезервированы и пока ведут к будущим файлам.

## Что означает общий статус и как читать приоритет

У большинства записей финальный `pausedReason=in-review-stall-deadlock`: Fusion оставлял шаги незавершёнными, не назначал remediation после REVISE либо повторно рассматривал не ту ветку, затем трижды получал `task has incomplete steps`. Это дефект процесса прохождения задачи; он не заменяет диагноз реализации. Там, где reviewer нашёл дефект/недостаток, он назван отдельно. Где review был `review-input-unprovable`, неполный checkout или допускаемый no-op, это также не объявляется отрицательным code verdict.

Следующий порядок — сначала не смешивать и не переносить вслепую повреждённые Fusion деревья, затем сверить актуальную upstream/PR-ветку и review, восстановить только предметные изменения, исправить доказанные блокеры и снова пройти корректные implementation → verification → review этапы. Исходные сообщения о зелёных checks относятся только к указанным историческим SHA; матрица **не утверждает**, что какой-либо PR зелёный на 2026-09-29.

Пять локальных кандидатов на интеграционной ветке `511163981` имеют иной статус, чем эта FAILED-матрица: это кандидаты, а не допуск к merge. Рекомендуемая последовательность: **1) RUS-1436** — зафиксировать целевой production-shaped regression и сверить актуальные review; **2) RUS-1443** — после него проверить изоляцию draft по account, stale uploads и межвкладочное восстановление; **3) CTN-009** — перенести только семь нужных файлов без повреждённых удалений, исправить замечания SDK/docs; **4) CTN-011** — отдельно закрыть URL/location/accessibility review; **5) CTN-176** — проверить доступность пункта Duplicate as Task и обычный Markdown subtype на актуальном коде. Порядок — практическая очередность проверки, не зависимость между карточками и не утверждение об их готовности. RUS-1436, RUS-1443 и CTN-176 не входят в эти 32 строки; CTN-009 и CTN-011 входят по inventory и описаны ниже. Для пяти кандидатов evidence фиксирует собственные тематические коммиты, но не свежую приемку после обновления upstream. Особенно: у CTN-009 имеются несохранённые локальные правки, а в исходном повреждённом worktree есть чужие удаления; не считать их удалениями по задаче. У CTN-011 собственные feature-коммиты отделимы от импортированного main.
