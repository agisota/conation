# CTN-017 — Recognize common forwarded-subject prefixes

## Situation

CTN-017 is imported from [Macro issue #5704](https://github.com/macro-inc/macro/issues/5704). It addresses inbound message parsing: `extract_reply_html` and `extract_reply_plaintext` in `crates/email_utils/src/body_replyless/` bypass quoted-content removal only for a subject beginning with the exact case-sensitive `Fwd:`. A forwarded message with a common `FW:` / lower-case variant can instead enter normal reply splitting, which may remove forwarded content from the parsed and search representations.

The task is paused with `pausedReason=duplicate-decision-required`; its source metadata identifies CTN-1043 as a 1.0 near-duplicate. CTN-1043 tracks PR [#5811](https://github.com/macro-inc/macro/pull/5811), the same issue and HTML/plaintext parser behavior. Its description records the proposed shared predicate `^\s*fwd?:` (case-insensitive), including false-positive coverage for `fwiw:`. That is a likely single implementation, not proof that the PR is merged or accepted. Preserve CTN-017's identity until an authorized duplicate decision records its outcome.

## Goal and user scenario

When a person receives a forwarded email whose subject is `FW:`, `fw:`, `fwd:`, or `Fwd:` (optionally preceded by whitespace), Macro must treat it as a forward for **body-replyless extraction**. Both HTML and plaintext paths must retain forwarded content instead of applying the ordinary reply splitter.

**Before:** subject `FW: project update` fails the exact `Fwd:` check; an ordinary quoted-content splitter can remove part of the forwarded body.

**After:** subject `  fW: project update` is recognized and both extractors return the forwarded body unchanged, bypassing quoted-content removal. Subject `fwiw: project update` is not a forward prefix and continues through ordinary reply splitting.

## Scope and boundaries

- Recognize only the specified common ASCII forms `Fwd:` and `FW:` without case sensitivity, and tolerate leading subject whitespace. The colon must immediately follow `fw` or `fwd` after that leading whitespace.
- Use one shared prefix predicate for both HTML and plaintext extraction; their classification behavior must agree. Verify through the public body-replyless behavior, not only a predicate unit test.
- Non-forward subjects retain existing reply-splitting behavior. `fwiw:`, `fwdish:`, `forward:`, `FWX:`, and similar words are not prefixes merely because they begin with `fw` / `fwd`.
- Do not add localized prefixes or change how the web composer generates a new forward subject.
- **CTN-018 boundary:** CTN-018 handles subjectless Reply / Reply All / Forward subject generation (`Re:` / `Fwd:`) in the web composer. CTN-017 handles recognition of the subject on inbound messages during body extraction. The contracts touch the string `Fwd:` but neither duplicates the other's implementation. A composer-generated subjectless forward (`Fwd:`) remains recognized by the detector; no CTN-018 code or subject fallback behavior is changed here.
- This task does not change trailing Unicode cleanup (CTN-016) or general email subject normalization.

## Acceptance

### Success

1. `Fwd:` / `fwd:` and `FW:` / `fw:` prefixes are recognized regardless of case, with optional leading subject whitespace.
2. For each positive prefix, both HTML and plaintext extraction return the forwarded input body unmodified, bypassing the normal quote/reply splitter.
3. Non-forward subjects—including a case such as `fwiw:`—continue through the existing splitter and quoted content is still removed as before.
4. HTML and plaintext are covered through their public extraction functions and show the same prefix classification. Missing/ordinary subjects retain existing behavior.
5. Tests assert body content before and after the splitter boundary so a parser cannot pass by merely echoing the input in every case.

### Failure cases / negative cases

- Prefix recognition remains case-sensitive or fails with leading whitespace.
- A partial word such as `fwiw:` or `fwdish:` is mistaken for a forward marker, or a prefix without the required colon is accepted.
- Only one extraction path changes, or the HTML and plaintext paths disagree.
- A non-forward message bypasses the splitter and leaves quoted content in parsed/search output.
- The composer-generated subject, localized prefixes, or CTN-018 subjectless fallback are changed as part of this parser fix.
- A second predicate/patch/PR is created while CTN-1043 / PR #5811 owns the same issue without an explicit duplicate resolution.
