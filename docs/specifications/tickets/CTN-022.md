## Original Description

<!-- fusion-original-description:start -->
**What happens**

Calling `ListEntities` with the `df` filter from an MCP client fails:

```
df: {"l":{"dst":"task"}}
  → unknown variant `{"l":{"dst":"task"}}`, expected one of `&`, `|`, `!`, `l`
```

The payload is exactly the syntax the tool's own description recommends for tasks. The client sent it as a JSON **string** rather than an object, and `Expr`'s deserializer then tried to read the whole literal as a variant name.

**Why**

The nine AST filter params on `ListEntities` (`df`, `pf`, `propf`, `ef`, `cf`, `chanf`, `cthf`, `callf`, `fef`) are declared with `with = "Option<serde_json::Value>"`. With schemars 1.0.4 that emits:

```json
"df": {
  "description": "Full soup AST document filter (df). …",
  "default": null
}
```

No `type` key. I reproduced this against schemars 1.0.4 in isolation — and note that a plain `Option<serde_json::Value>` without the `with` attribute emits the same thing, so the attribute isn't the cause; schemars renders `Value` as an unconstrained "any" schema. That's valid JSON Schema, but an LLM client building arguments from it has no signal that an object is expected, so it stringifies.

This affects any client that constructs arguments from the advertised schema, not one specific client.

**Impact**

AST-based filtering is unreachable from MCP. The typed params (`includeTypes`, `tags`, `emailPreset`, `inbox`) work fine, so this is recoverable — I can pass `includeTypes: ["document"]` and filter `subType == "task"` client-side. But:

- `limit` is clamped to `MAX_RESULT_LIMIT` (500) and there's no cursor/offset field, so the budget applies to the *unfiltered* document set. Past 500 documents, task coverage can't be guaranteed with `sortBy: recently_updated`.
- It blocks the time-bounded filtering the `df`/`ef` descriptions document (`ua`/`ca` with `gte`/`lt`), which is the natural incremental-sync path.

**Suggested fix**

Give these fields a concrete schema rather than deferring to `Value`. Even `"type": "object"` would stop clients stringifying. Deriving `JsonSchema` on `Expr` / `DocumentLiteral` et al. would be better still — clients could then construct valid filters from the schema instead of parsing the prose examples in the descriptions.

**Environment**

Hosted `https://mcp-server.macro.com/mcp`, via Claude Code. Source read at `4067868`.

## Mission

Fix `ListEntities`'s `JsonSchema` representation for the nine `LiteralTree<T> = Option<Arc<Expr<T>>>` parameters in `crates/soup/src/inbound/toolset/list_entities.rs`, without converting argument strings at runtime or changing the filter execution semantics. `filter_ast::Expr` and the literal types in `item_filters::ast` deserialize the real nested JSON AST; `ai_toolset::schema::generate_validated_input_schema` constructs the tool input schema, `ai_tools::tools_for(AiHost::Mcp)` registers it, and `AuthenticatedToolService::tool_definitions` advertises it to MCP clients.
