# CTN-039 — Static authentication headers for remote MCP connectors

## Situation and provenance

CTN-039 was imported from [macro-inc/macro#5465](https://github.com/macro-inc/macro/issues/5465). The user reports that Settings → Connectors → Add server accepts only a name and URL, leaving remote MCP servers unreachable when they require a static API key, bearer token, or other custom HTTP request header rather than OAuth. The requested capability is per-connector credentials, with custom key/value request headers as the most flexible representation. The request explicitly excludes `stdio`.

The source task is paused with `pausedReason=duplicate-decision-required` and names RUS-161 as an exact duplicate (`nearDuplicateScore: 1`). RUS-161 owns the same source issue via PR #5582 and specifies persistent connector headers, Add Server and Configure Headers UI, API types, request transport, and schema/generated types. Its task record still has unfinished API/transport, schema, test, and delivery steps and is paused in review with an unresolved review-input failure. Therefore, CTN-039's user request should be consolidated under RUS-161, not implemented independently or described as delivered. Keep CTN-039 visible as the originating duplicate record; do not treat the PR or its task description as evidence of merge, deployment, or verified behavior.

## Goals

- Let a user configure static HTTP request headers for a remote MCP connector so it can authenticate to a third-party MCP server that does not use Macro's OAuth connection flow.
- Persist header configuration per server and have the outbound Streamable HTTP transport send only the configured headers to that connector's requests.
- Make credentials manageable on both new and already-connected remote servers, consistent with the source request and RUS-161 design.
- Ensure secret-bearing header values are treated as credentials: do not expose them through logs, errors, screenshots, source-controlled examples, or ordinary server-list responses. Resolve and prove the actual at-rest protection behavior before claiming it.
- Keep RFC 9728 protected-resource `resource` metadata, Macro's OAuth client-registration credentials, and outbound static headers semantically and operationally separate.

## Non-goals and boundaries

- No `stdio` support; the source explicitly excludes it.
- No replacement of OAuth, OAuth DCR, OAuth authorization-code/client-secret handling, token refresh, or RFC 9728 discovery with static headers.
- No static credential field is added to RFC 9728 metadata. `resource` remains the URL-valued identifier of Macro's own protected resource, not a token, header name, or header value.
- CTN-034 owns the separate OAuth case: user-supplied OAuth `client_id` / `client_secret` for a remote authorization server that lacks Dynamic Client Registration. Those OAuth client credentials participate in the OAuth authorization/token flow; RUS-161/CTN-039 headers are request headers attached to the remote MCP transport. Do not coerce one mechanism into the other.
- No promise that arbitrary upstream auth protocols, OAuth providers, or malformed headers can be supported. The source request covers static HTTP headers for remote MCP servers.
- This specification does not decide deployment, database migration rollout, generated-client publishing, or production enablement.

## User scenario and expected behavior

A user chooses a remote HTTP MCP server whose documented authentication requires static request headers, enters the server name/URL and required header pairs in the Add Server flow, and connects. Macro persists those settings with that user's connector. Subsequent MCP requests for that connector carry the configured headers. The user can later inspect and change header configuration for an existing connector. If the upstream rejects or the headers cannot be safely represented, the connection must fail visibly without leaking the entered values.

The same URL may be used by multiple users with different credentials: one user's headers must never be applied to another user's connector. Header values are secret input even when a header name is non-secret.

## Acceptance

### Success

1. Add-server UI accepts zero or more custom header name/value pairs for remote HTTP MCP connectors; users can add/remove rows and submit. Existing OAuth-oriented add/authorization behavior continues to work when static headers are not supplied.
2. An existing connected server exposes a clear configuration action to view/edit its headers. A save changes the correct user/server record and subsequent requests use the saved values; removal stops sending removed values.
3. An authenticated upstream fixture accepts a configured non-OAuth header and the connector completes MCP initialization and a representative tool request. The observed outbound request has the intended header name and value, and no unrelated connector receives it.
4. A fixture that rejects missing or incorrect auth returns the ordinary connection/request failure path; it does not falsely display the connector as authenticated or connected. Correcting the stored header and retrying can proceed through initialization and the representative request.
5. Header persistence survives load/restart according to the supported store. Database readback and transport behavior agree with the saved record. Concurrent saves/credential refreshes do not silently replace headers with an empty/default map or lose an independent update.
6. Persistence review confirms the secret values receive the approved credential protection at rest. Tests inspect the raw stored representation and prove that supplied secret material is not present as plaintext where encryption is required. If the existing design does not protect header values, stop and resolve the security contract before declaring success rather than silently describing JSONB storage as encrypted.
7. API and ordinary list/read responses reveal only the explicitly intended representation; credentials are redacted or omitted from logs, error strings, tracing, generated diagnostics, and user-visible screenshots. A user can edit configured headers without needing a secret echoed back to the client.
8. Valid header names and values reach the HTTP transport unchanged. Invalid names/values are rejected or omitted according to one explicit, tested policy and reported without exposing values; silently forwarding malformed headers is failure. Follow the owning implementation's chosen validation semantics and keep API/UI behavior consistent.
9. Empty headers preserve existing behavior. OAuth discovery and authorization remain available and unchanged for connectors that use OAuth.

### Failure

- Header data crosses user/server boundaries, is attached to a different connector, or appears in ordinary logs, error text, task docs, screenshots, examples, fixtures committed with values, or unredacted list responses.
- A saved header appears in storage but is absent from the actual outbound request, or an unsaved/removed value is still sent.
- An upstream authorization failure is reported as successful connection, or a successful fixture only proves UI/API echo rather than the transport's actual request.
- Adding custom-header support disables existing OAuth setup, confuses an OAuth `client_id` / `client_secret` with a request header, or puts any credential into RFC 9728 `resource` metadata.
- Persistence, callback/refresh, or competing updates replace configured headers without a tested conflict policy.
- Tests merely assert serialization, non-empty fields, mocked echoes, or that code does not throw; they do not prove per-user/per-server isolation and the outbound auth success/failure behavior.
- The duplicate is described as completed solely because RUS-161 has PR #5582 or a historical task proposal.
