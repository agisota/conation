# CTN-037 — RFC 9728 resource metadata for Macro MCP

## Situation and provenance

CTN-037 was imported from [macro-inc/macro#5519](https://github.com/macro-inc/macro/issues/5519). Its reported defect is specific: strict MCP clients (the source names Grok Build / `rmcp` 2.1.0) reject OAuth discovery when Macro's OAuth protected-resource metadata omits RFC 9728's required `resource` member. The source identifies three discovery paths—`/.well-known/oauth-protected-resource`, `/.well-known/oauth-protected-resource/mcp`, and `/mcp/.well-known/oauth-protected-resource`—and says they should advertise the same protected resource.

The source proposes deriving the resource URL from existing `MCP_PUBLIC_URL`, retaining singular and plural authorization-server fields, recommending `resource_name`, and not inventing `scopes_supported` because Macro has no resource-level MCP scopes. This is an OAuth discovery contract, not a place to configure or store credentials sent to a remote MCP server.

## Goals

- Define the protected-resource metadata contract for Macro's MCP endpoint in accordance with RFC 9728 §3.3.
- Ensure `resource` identifies the actual protected MCP resource URL that the client is connecting to, rather than the OAuth authorization server or an auth credential.
- Preserve compatibility fields already consumed by clients and avoid claiming unsupported MCP scopes.
- Record observable discovery and OAuth-flow success/failure checks so the duplicate can be verified through its owning RUS-217 delivery.

## Non-goals

- No new configuration, endpoint, credentials, request-header behavior, MCP connector UI, or storage is introduced by CTN-037.
- Do not change RFC 9728 `resource` into an API token, bearer value, custom header, connector setting, OAuth client ID, or client secret. It is a URL-valued identifier for the protected resource.
- Do not add `scopes_supported` until Macro defines actual resource-level MCP scopes. FusionAuth identity scopes are not a substitute.
- No changes to CTN-034's OAuth client registration flow or RUS-161's remote-connector headers.
- No claim of production deployment or a successful live client connection without direct evidence.

## User scenario and boundary

A user adds Macro MCP at `https://mcp-server.macro.com/mcp` in a strict OAuth-capable MCP client. The client receives an authentication challenge, follows the advertised protected-resource metadata location, validates the metadata, discovers the authorization server, then proceeds with the existing OAuth flow. Metadata validation must no longer stop at a missing `resource` field.

Boundary: CTN-037 concerns Macro acting as the protected MCP server and describing its own resource to OAuth clients. RUS-161 concerns credentials a Macro user supplies when Macro connects outward to a third-party MCP server. CTN-034 concerns OAuth client registration/credentials for a remote server that cannot dynamically register an OAuth client. Those values and flows must remain distinct.

## Acceptance

### Success

1. Each of the three discovery paths listed in the source resolves successfully and returns a JSON metadata document with a non-empty `resource` value equal to the canonical MCP resource URL being accessed (for the production example, `https://mcp-server.macro.com/mcp`). It is the resource URL, not the authorization-server base URL.
2. A `MCP_PUBLIC_URL` configured at the origin produces the `/mcp` resource path; one already ending in `/mcp` does not produce `/mcp/mcp`. Trailing-slash/path handling must be tested against the actual accepted configuration contract; a mismatch between the client's resource URL and metadata `resource` is a failure, not something to hide with a loose-prefix comparison.
3. The document preserves `authorization_server` and `authorization_servers` with the existing authorization-server value for compatibility. It may include `resource_name` as the source recommends. It omits `scopes_supported` while no MCP resource scopes exist.
4. An OAuth client that previously stopped with “Protected resource metadata missing required resource field” passes metadata validation and proceeds to the next existing authorization step. This is not by itself proof of a completed login, consent, token exchange, or deployed behavior.
5. An unauthenticated request through each advertised discovery URL and route tests must observe the same required `resource` contract. A live check, if performed during the owning RUS-217 delivery, records the exact URL, status, and field presence without storing response credentials.

### Failure

- Missing, empty, malformed, wrong-origin, wrong-path, or double-appended `resource` fails acceptance; a strict client must not be made to accept an incorrect resource identifier.
- Any discovery alias returns a different protected resource or lacks the required member.
- The implementation invents `scopes_supported`, advertises the authorization server as if it were the protected MCP resource, or changes authentication semantics to compensate.
- A test-only result, task status, PR description, or local checkout is represented as proof of production deployment or successful end-to-end OAuth.
