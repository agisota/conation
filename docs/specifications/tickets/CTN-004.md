# CTN-004 — Official prebuilt Docker images for self-hosting

## Situation and source

CTN-004 is based on GitHub issue [macro-inc/macro#6447](https://github.com/macro-inc/macro/issues/6447). The reporter wants to deploy Macro on a Synology NAS, Unraid, Proxmox, a small home server, or a small-business host without compiling Rust services or assembling infrastructure manually. Their concrete first-run expectation is `docker compose pull` followed by `docker compose up -d`, using official prebuilt images.

The Fusion card has no declared task dependencies or implementation steps. It is paused with `duplicate-decision-required`; its `sourceMetadata` marks CTN-816 as a near duplicate (score 1) but explicitly says that marker has not been dismissed. This is a triage signal, not a decision that the work is already delivered.

CTN-816 is the PR-feedback card for draft PR [#6046](https://github.com/macro-inc/macro/pull/6046). Its proposed `self-host/` deployment already includes an image workflow publishing service, web, init, and worker images to GHCR on a tag, plus Compose and operator tooling. Its own description says those images had not been built and that the stack had not been brought up on a real host. Therefore CTN-004 must not create a second image pipeline or a competing Compose deployment. First establish the disposition and current state of PR #6046 and its image artifacts; carry any unmet CTN-004 acceptance into that single deployment path.

[RUS-1448 — DEP-02 Production self-host profile](../tickets/RUS-1448.md) is related but is not recorded as CTN-004's dependency or duplicate: its `nearDuplicateOf: CTN-816` marker is explicitly dismissed, and it declares dependency RUS-1447. RUS-1448 owns the production runtime contract—service/dependency selection, persistent volumes, migrations, install/upgrade lifecycle, health/readiness, and production configuration—and excludes local boot stubs, dev auth/test keys, debug exposure, and reset behavior. CTN-004 owns the official prebuilt-image delivery and no-toolchain consumption outcome. The image set and references must satisfy the production profile rather than making a dev/local stack appear production-ready. Do not change RUS-1448's dependency graph through this specification.

## Goal and boundaries

Provide a supported, versioned set of official prebuilt container images and a checked-in deployment configuration that a self-host operator can pull and run without building Macro from source or installing a Rust, Nix, or Node toolchain on the host.

In scope:

- Publish every container image required by the supported self-host Compose deployment as official release artifacts, including the service, web, initialization, and worker images identified by the existing CTN-816 design, or document a source-backed reason for any image not used by the final RUS-1448 profile.
- Make release tags and the Compose references unambiguous and consistent so an operator can pull one compatible release set. Define how an operator selects/updates a release; do not imply an unverified floating `latest` tag.
- Keep the actual production deployment contract under RUS-1448 and its owned service/configuration tasks. Image delivery does not authorize including unsupported product capabilities or hidden dev-only fallbacks.
- Document the supported first install, update, and host prerequisites in the existing self-host deployment documentation; maintain the simple pull-and-start path where compatible with required configuration and safe lifecycle steps.

Out of scope:

- A second self-host stack, second image workflow, or separate image namespace for the same deployment.
- Implementing production profile requirements assigned to RUS-1448/RUS-1447 or its dependent owners merely to close this issue.
- Promising Synology/Unraid/Proxmox-specific certification, every CPU architecture, high availability, paid support, HIPAA/compliance status, or capabilities excluded from the production profile. State tested platform/architecture coverage from actual CI/runtime evidence only.
- Treating `just run_local`, development images, or local-stack binaries as a supported production install solely because they are containerized.

## Acceptance

### Success

1. There is one authoritative self-host Compose deployment and one release image workflow. The workflow publishes the exact image set referenced by that deployment for a release, with a documented versioned tag convention and compatible references across all required images. No required service reference points to a local-only build or an undocumented floating tag.
2. A clean supported host can fetch the published release images (`docker compose pull`) and start the documented production profile using only Docker/Compose and documented operator inputs. No Rust/Nix/Node build toolchain or source checkout is needed on that host. Any prerequisite configuration or migration/upgrade command is explicit rather than hidden behind the two-command shorthand.
3. The running containers use the just-pulled release images and the production configuration owned by RUS-1448: durable state is attached to the declared persistent storage, required dependencies report readiness, and no dev-auth/test-key/local-override fallback is silently enabled. Image publishing alone is not evidence that the production profile is correct.
4. The published release artifacts and deployment documentation identify supported host architecture(s) and the tested release tag. Claims for NAS-specific compatibility are limited to platforms actually exercised.
5. The disposition of CTN-004 and CTN-816 is recorded: either CTN-004's image-delivery acceptance is met by the single reviewed/landed CTN-816 deployment path, or a specific unmet criterion remains assigned to that same path. A duplicate marker alone does not count as delivery.

### Failure

- A release fails acceptance if a required image is missing, has no corresponding compatible release tag, or Compose points at a tag that cannot be pulled from the official registry.
- A clean-host pull or startup that requires compiling images locally, an undocumented source checkout/toolchain, or a private credential not listed in the operator prerequisites fails.
- Startup that selects dev auth/test keys, local boot stubs, or another forbidden development fallback fails closed with an actionable configuration/readiness error; it must not be reported as a successful production install.
- Missing durable storage or a required service/dependency that never becomes ready must be observable as a failed install/start, not a healthy-looking partial deployment.
- A duplicate workflow/Compose stack or claims of supported architectures/features without evidence fail review; do not mask these by weakening the supported deployment contract.

## Verification scenarios

Use a disposable supported host/environment and a release candidate; do not destroy or reset operator data as part of testing.

- **Release-artifact smoke:** Trigger the release workflow for a test/release tag and verify the registry contains every required service, web, init, and worker image for the documented architecture(s), all carrying the expected release tag. Verify the workflow fails when a required image build/publish step fails.
- **Clean-host install:** With Docker/Compose but no source checkout or language toolchains, supply only documented prerequisites, run the documented setup and `docker compose pull`, then start the profile. Confirm Compose resolves every image from the registry and containers report healthy/readiness only when required dependencies are ready.
- **Persistence/restart:** Write disposable test data, restart the Compose project without deleting named volumes, and verify the data remains. Confirm no routine install/update command removes volumes.
- **Failure smoke:** Use a nonexistent image tag and verify `pull`/startup fails visibly with the unresolved image, not a successful partial deployment. Omit a required production setting or make a mandatory dependency unavailable and verify startup reports the specific missing/failed prerequisite without enabling dev fallback.
- **No-toolchain check:** Run the documented host procedure in an environment with no Rust, Nix, or Node installed and no source tree mounted; it must still pull and start the published deployment.
- **Upgrade smoke:** Follow the documented release update procedure from one disposable tag to another; verify the running image set changes coherently and persistent data survives. Verify a failed pull/upgrade does not silently destroy data or claim a completed upgrade.
