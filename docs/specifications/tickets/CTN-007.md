## Goal and original user request

## What This Delivers

People with personal email addresses can be added to a team's pipeline as individuals, without pretending everyone using the same email provider works for one firm. Firm records and the existing automatic directory remain unchanged. The import can create and find those people, and teammates can see them in the people list and open their records.

## Original Description

<!-- fusion-original-description:start -->
I'm importing attorney and law-firm data into Macro's CRM via the TypeScript SDK (`packages/sdk`) for my startup, DefenseBridge. The goal is a usable pipeline of firms and the individual attorneys at them.

Two SDK constraints block part of the data. `macro.crm.createCompany({ domain, name })` rejects generic email-provider domains, and `company.createContact({ email, name })` requires the contact's email domain to match the company's domain. The domain check lives in `crates/crm/src/domain/generic_email_domains.rs`. In my dataset of 4,009 attorney contacts across 2,878 firms, 317 contacts at 309 firms use personal addresses (gmail.com, yahoo.com, etc.). It's 8% of contacts, but they skew toward solo practitioners, which is the segment I'm targeting. None of them can exist in the CRM at all, even though they're the people I need in the pipeline.

Anyone selling to freelancers, consultants, or creators hits the same wall: the CRM currently models companies only, and a large share of independent professionals have no company domain.

Two possible directions:

- **Personal contacts.** Let a contact exist without a company, or auto-file personal addresses under a per-team "Individuals" bucket. Keeps the domain directory clean, but adds a second record type to the board and list views.
- **Opt-in generic domains.** A per-team setting that allows company creation from generic domains, off by default. Minimal schema change, but risks the problem the filter exists to prevent, where one generic domain becomes a company with thousands of unrelated contacts.

I'm not proposing changing the default domain-directory behavior for everyone.

Happy to implement whichever direction you'd prefer once there's alignment.

Source: https://github.com/macro-inc/macro/issues/6344

## Mission

Choose the reporter's **personal-contacts / per-team Individuals bucket** direction, not generic-domain opt-in: expose an explicit `POST /crm/contacts` and `macro.crm.createContact({ email, name })` for manually entered people using domains recognized by the existing generic-email-provider classifier. Back contacts with one uniquely identified, domainless, non-syncing, manually retained Individuals container per team so existing `crm_contacts.company_id` and contact access/favorites/comments remain valid. Treat the container as implementation plumbing rather than a firm: contacts show as individuals in the people directory and detail, while domain-keyed company creation and company-bound contact creation retain their current guards. **Identity policy:** an eligible normalized email belongs to at most one contact in a team across both the bucket and any existing company (including hidden rows); return 409 on collision, never create an ambiguous second contact or silently move an existing firm contact. This decision does not promise that a personal-address attorney is attached to a particular real firm; do not silently represent a generic provider as that firm. Non-generic addresses use the existing company flow; this avoids future domain-populate creating a second identity for a bucket contact. Existing historical duplicates, if any, are not silently migrated by this task.
