# CTN-015 — Clear run-local failure when frontend dependencies are missing

## Situation and source

CTN-015 comes from [macro-inc/macro#5788](https://github.com/macro-inc/macro/issues/5788). The reported reproduction is a fresh checkout where the user enters `nix develop` and runs `just run_local --no-doppler` without first running `bun install`. Backend services come up, but `apps/web/node_modules` is absent; the frontend start path spawns `bun run dev`, polls readiness for about 36 seconds, then reports only `frontend dev server did not become ready`. The proposed fix is a pre-start prerequisite check that tells the user to run `bun install` from the repository root.

The Fusion card declares no dependencies or execution steps. It is paused with `duplicate-decision-required`; `sourceMetadata` identifies RUS-011 as a near duplicate (score 1), but the marker is not dismissed. RUS-011 is not a general product feature: it is the review/CI task for PR [#5789](https://github.com/macro-inc/macro/pull/5789), explicitly sourced from issue #5788. Its described work includes both (a) a clear missing-`node_modules` error and (b) prebuilding `cache-wasm` and `agent-fold` before readiness polling on a cold WASM cache. The first is CTN-015's entire contract; the second is adjacent startup/readiness work in the RUS-011 PR and must not be mislabeled as a CTN-015 requirement.

This is an informative, narrow bug specification. Check the current RUS-011/PR state before implementation. If the missing-install behavior is already landed and passes the scenarios here, record CTN-015 as satisfied by that source and do not duplicate the code change. If it is absent, implement only the prerequisite diagnostic described here and keep cold-WASM handling scoped to RUS-011.

## Goal and boundaries

When the frontend cannot start because its installed web dependencies are missing, fail immediately before spawning the frontend process and report the precise prerequisite and recovery command. Preserve the existing `run_local` startup behavior when dependencies are installed.

In scope:

- Check for the exact frontend installation prerequisite, `apps/web/node_modules`, before starting `bun run dev`.
- Report that the frontend dependencies are missing and tell the operator to run `bun install` from the repository root.
- Preserve normal frontend startup/readiness behavior when the prerequisite exists.

Out of scope:

- Automatically installing dependencies, changing package management, or running install commands as a side effect of `run_local`.
- Replacing the targeted prerequisite check with generic retries, a longer port timeout, or suppression of the readiness error.
- Cold WASM build duration/cache behavior (the separate prebuild behavior described by RUS-011), backend service behavior, or general Nix setup changes.

## Acceptance

### Success

1. On a fresh checkout with no `apps/web/node_modules`, `just run_local --no-doppler` detects the missing path before spawning `bun run dev` or entering the frontend port-readiness wait. It exits the frontend startup step promptly with a useful message that names `apps/web/node_modules` and says to run `bun install` from the repository root.
2. The missing-install failure does not present the generic “frontend dev server did not become ready” timeout as the primary diagnosis, and does not leave a frontend child process running. Other services already started by `run_local` are not silently claimed to have failed for this frontend-specific reason.
3. With frontend dependencies installed, the same command continues to spawn the frontend and uses its existing port/readiness contract; the new check does not turn a normal installed checkout into an error.
4. The diagnostic is tied to the missing directory itself. A present `apps/web/node_modules` directory must not be rejected merely because its contents are imperfect; failures beyond this prerequisite continue through existing startup errors rather than claiming the directory is absent.
5. The `run_local` command does not run `bun install` automatically. The diagnostic gives a user-controlled remedy and does not alter dependency lockfiles or environment state.

### Failure

- Missing dependencies that still incur the existing roughly 36-second generic readiness wait fail acceptance: the guard must run before child startup/polling.
- A message that reports only a port timeout, hides the missing path, or omits the root-level `bun install` remedy fails acceptance.
- If `bun run dev` is launched when `apps/web/node_modules` is absent, startup fails acceptance even if the process later exits on its own.
- If installed dependencies are present but frontend startup fails for another reason, reporting “node_modules is missing” is a false diagnosis and fails acceptance.
- Automatically installing dependencies, retrying indefinitely, or broadening the ticket to cold-WASM compilation is not an acceptable substitute for this targeted error contract.
