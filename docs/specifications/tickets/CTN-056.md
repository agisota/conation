Stacked on #6826. The five calendar mutation `utoipa::path` annotations in `calendar_events::inbound::mutation_router` carried a `/calendar` prefix because email-service listed them under `/email/calendar/*`. #6826 removes them from email's spec, so the prefix no longer does anything. The routes themselves are registered with plain `.route("/calendars" | "/events" | …)`, so the annotations were only documentation. calendar_service still mounts the router at `/` and under `/calendar` (`mount_at_root_and_prefix`), so gateway traffic on `<gateway>/calendar/*` and the target group's root `/health` check are unchanged.

With the annotations root-relative, the SDK no longer needs to rewrite calendar's spec. `sync-specs.ts` drops `stripCalendarPrefix` / `syncCalendarSpec` (the `cargo run --bin calendar_service_openapi` path) and copies `calendar.json` from apps/web's `service-calendar` client, which #6826 added, like every other service. The regenerated `packages/sdk/specs/calendar.json` differs only in JSON formatting (`jq -S` output is identical), so `packages/sdk/generated` doesn't change and no version bump is needed. `package.json` is still the unreleased `0.1.0`.

Also fixed:
- `packages/sdk/src/config.ts`: the local calendar base is `http://localhost:8088/calendar` (calendar_service in the local stack since #6755) instead of email-service's 8087, and the comment claiming calendar_service isn't in the local stack is rewritten. This now matches apps/web's `servers.ts`.
- The calendar_service swagger and gateway-prefix doc comments no longer describe the cutover.
- `calendar_events`' `mutation-client` feature comment and `CalendarServiceMutations`' transport error message said "email service"; that client talks to calendar-service.
